# Architecture Decision — Banking Write Operasyonlarını Transaction Sınırı İçinde Çalıştırmak

- **Tarih:** 08-13
- **Durum:** Kabul edildi

## Bağlam

Bankacılık uygulamasındaki bazı servis operasyonları birden fazla kalıcı veritabanı değişikliği içerir.

Örnek transfer akışı:

```text
Sender account balance update
Receiver account balance update
Transaction insert
```

Müşteri kayıt akışı:

```text
Customer insert
Account insert
```

Deposit ve withdrawal işlemleri de account update ile transaction insert işlemlerini birlikte gerçekleştirir.

Bu işlemlerden yalnızca bir kısmının başarıyla kaydedilmesi veri tutarsızlığı oluşturabilir.

## Karar

Çok adımlı write operasyonları `BankService` seviyesinde Spring transaction sınırı içine alınacaktır.

Aşağıdaki methodlarda:

```java
@Transactional
```

kullanılacaktır:

```text
registerCustomer
depositToAccount
withdrawFromAccount
transferFromAccount
```

Read servis methodları bu aşamada transaction annotation’ı ile işaretlenmeyecektir.

## Gerekçe

Transaction sınırı application service seviyesindeki use case’i kapsamalıdır.

Örneğin transfer tek bir business operation’dır:

```text
Transfer money
```

Bu use case’in persistence tarafında birden fazla write gerçekleştirmesi teknik bir ayrıntıdır.

Bu nedenle transaction sınırının tek tek repository methodlarında değil, bütün operation’ı yöneten `BankService` methodunda bulunması tercih edilmiştir.

## Beklenen Davranış

```text
Bütün database write işlemleri başarılı
→ COMMIT

Write işlemlerinden biri başarısız
→ ROLLBACK
```

## Sonuçlar

### Olumlu

- Transfer atomic hale gelir.
- Customer + Account creation birlikte yönetilir.
- Account update ile transaction insert birlikte yönetilir.
- Persistence tutarlılığı güçlenir.
- Transaction sınırı business use case seviyesinde görünür.

### Dikkat Edilecek Noktalar

- Spring transaction yönetimi `BankService` seviyesinde kullanılmaktadır.
- Gerçek rollback davranışının integration test ile ayrıca doğrulanması faydalıdır.
- Uzun süren transactionlardan kaçınılmalıdır.
