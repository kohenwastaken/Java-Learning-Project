# Architecture Decision — ID Üretimini Persistence Katmanının Sorumluluğuna Vermek

- **Tarih:** 08-06
- **Durum:** Kabul edildi

## Bağlam

Mevcut `BankService`, müşteri ve transaction ID’lerini application katmanındaki sayaçlarla üretmektedir:

```java
private int userId = 1;
private int transactionId = 1;
```

Bu yaklaşım InMemory kullanımda yeterli olsa da uygulama yeniden başladığında sayaçların sıfırlanması PostgreSQL’de mevcut primary key değerleriyle çakışma riski oluşturur.

İlk çözüm olarak domain modellerinde:

```text
0 = henüz ID verilmedi
```

yaklaşımı değerlendirildi.

Ancak bunun persistence lifecycle bilgisini domain modeline taşıdığı görüldü.

## Karar

ID üretimi application service’in sorumluluğundan çıkarılacaktır.

```text
PostgreSQL adapter
→ ID üretimini PostgreSQL’e bırakır

InMemory adapter
→ ID üretimini kendi içinde yapar

BankService
→ ID üretim mekanizmasını bilmez

Domain modelleri
→ PostgreSQL veya ID-generation stratejisini bilmez
```

PostgreSQL persistence entity’lerinde generated primary key yaklaşımı kullanılacaktır.

Domain içinde:

```text
0 = ID yok
```

gibi sentinel/magic value kullanılmayacaktır.

Yeni kayıt oluşturma ihtiyacı repository portunda ayrı bir operasyonla ifade edilebilecektir:

```java
Customer create(
        String name,
        String surname,
        String password
);
```

## Gerekçe

- Application service’in persistence durumunu takip etmesini önlemek
- Uygulama restartlarında primary key çakışmasını engellemek
- Hexagonal architecture sınırlarını korumak
- Domain modellerinin PostgreSQL ve JPA lifecycle ayrıntılarından bağımsız kalması
- InMemory ve PostgreSQL adapterlarının kendi teknik gereksinimlerini kendi içinde yönetebilmesi
- Persistence mekanizmasının ileride değiştirilebilmesini kolaylaştırmak

## Customer ve Account Kimliği

Mevcut projede Customer ve Account aynı ID değerini paylaşmaktadır.

Daha gerçekçi bir tasarımda bu kimlikler ayrı tutulabilir ve Account üzerinde customer foreign key’i bulunabilir.

Ancak mevcut aşamada bu değişiklik geniş kapsamlı refactor gerektireceği için yapılmayacaktır.

```text
Customer ID = Account ID
```

varsayımı proje kapsamında korunacaktır.

## Sonuçlar

### Olumlu

- BankService ID sayacı tutmak zorunda kalmayacaktır.
- PostgreSQL primary key üretimini merkezi olarak yönetebilecektir.
- Domain modellerine persistence kaynaklı magic value eklenmeyecektir.
- InMemory adapter bağımsız biçimde test ID’leri üretebilir.
- Persistence stratejisi application ve domain katmanlarından ayrılmış olur.

### Maliyet

- Repository portlarına yeni create operasyonları eklemek gerekebilir.
- InMemory repository’lerde ayrı ID sayaçları tutulacaktır.
- PostgreSQL adapterlarında generated ID’nin tekrar domain modeline dönüştürülmesi gerekir.
- Mevcut Customer–Account ortak ID modeli ileride genişletilmek istenirse ayrıca refactor gerekecektir.
