# 08-06 — Hexagonal Architecture Sınırları ve Tasarımın Geri Alınması

## Günün Amacı

Bu çalışmada ID üretimini PostgreSQL’e taşırken yapılan ilk tasarım denemesi değerlendirildi.

İlk yaklaşım teknik olarak çalışabilecek olsa da domain modeline persistence ayrıntısı taşıdığı fark edildi ve commitlenmeden geri alındı.

Bu süreç, hexagonal architecture’ın neden kullanıldığını daha net anlamayı sağladı.

---

## İlk Denenen Yaklaşım

Yeni müşterinin henüz gerçek ID’si olmadığı için `Customer` sınıfına ikinci constructor eklenmesi düşünüldü:

```java
public Customer(
        String name,
        String surname,
        String password
) {
    this(name, surname, password, 0);
}
```

Burada:

```text
ID = 0
```

değeri:

```text
Henüz gerçek ID verilmedi
```

anlamında kullanılacaktı.

Bu yaklaşım constructor overloading ve `this(...)` constructor çağrısının nasıl çalıştığını da gösterdi.

---

## Constructor Overloading

Aynı class içinde farklı parametre listelerine sahip birden fazla constructor bulunabilir.

Örnek:

```java
public Customer(
        String name,
        String surname,
        String password,
        int accID
) {
    ...
}
```

ve:

```java
public Customer(
        String name,
        String surname,
        String password
) {
    this(name, surname, password, 0);
}
```

İkinci constructor içindeki `this(...)`, aynı class’ın diğer constructor’ını çağırır.

---

## Neden Bu Tasarım Geri Alındı?

`0 = henüz ID yok` yaklaşımı persistence ihtiyacından doğuyordu.

Domain `Customer` sınıfının:

```text
PostgreSQL ID üretmeden önce ID yoktur
```

gibi bir altyapı ayrıntısını bilmesi istenmedi.

Bu nedenle `0` değeri bir sentinel/magic value hâline geliyordu:

```text
0   → gerçek ID değil
1+  → gerçek ID
```

Bu ayrım domain modeline persistence lifecycle bilgisi taşıyordu.

---

## Hexagonal Architecture’ın Buradaki Rolü

Hexagonal architecture’ın amacı yalnızca frontend veya backend teknolojisi değiştiğinde kodu korumak değildir.

Asıl hedef:

```text
Domain ve application katmanlarını
dış teknoloji ayrıntılarından mümkün olduğunca bağımsız tutmak
```

olarak değerlendirildi.

Domain’in şunları bilmesi istenmez:

```text
PostgreSQL kullanılıyor mu?
JPA kullanılıyor mu?
Veriler Map içinde mi?
ID’yi hangi veritabanı üretiyor?
REST mi CLI mı kullanılıyor?
```

Bu bilgiler adapter ve infrastructure tarafında kalmalıdır.

---

## Domain Ne Zaman Değişebilir?

Hexagonal architecture:

```text
Domain hiçbir zaman değişmez
```

anlamına gelmez.

İş kuralı değişirse domain değişebilir.

Ancak:

```text
PostgreSQL ID üretmek istiyor
```

bir iş kuralı değil, persistence ayrıntısıdır.

Bu nedenle yalnızca bu sebeple domain modelini değiştirmemek tercih edildi.

---

## Git ile Değişiklikleri İnceleme

Commitlenmemiş değişiklikleri görmek için:

```bash
git diff --name-only
```

kullanıldı.

Bu komut son commit’ten sonra değişmiş dosyaları listeler.

Transaction sınıfı listede olmadığı için onun değiştirilmediği anlaşıldı.

---

## `git restore`

Yanlış yönde ilerlediğine karar verilen ancak henüz commitlenmemiş dosyalar:

```bash
git restore <dosya>
```

ile son commit’teki hâllerine döndürüldü.

Bütün proje için:

```bash
git restore .
```

kullanılmadı.

Bunun nedeni ilgisiz başka uncommitted değişikliklerin yanlışlıkla silinmesini önlemekti.

---

## Yeni Tasarım Kararı

Domain modeline `ID = 0` gibi özel durumlar eklemek yerine repository portunun yeni kayıt oluşturma sorumluluğunu taşıması planlandı.

Kavramsal olarak:

```text
BankService
→ customerRepository.create(name, surname, password)
→ persistence adapter
→ ID üretimi
→ Tam Customer geri döner
```

PostgreSQL adapter:

```text
ID’siz persistence entity oluşturur
→ PostgreSQL ID üretir
→ ID’li entity döner
→ Customer domain modeline çevrilir
```

InMemory adapter ise aynı portu uygular ancak kendi ID sayacını kullanabilir.

---

## Customer ve Account ID’lerini Ayırma Konusu

Daha gerçekçi bir banka modelinde `Customer ID` ve `Account ID` ayrı kimlikler olabilir.

Örnek:

```text
Customer ID = 5

Account ID = 17
customer_id = 5
```

Bu yapı bir müşterinin birden fazla hesabı olmasına izin verir.

Mevcut projede ise:

```text
Customer ID = Account ID
```

modeli kullanılmaktadır.

Bu ayrımın değiştirilmesi domain modelleri, repository’ler, BankService, REST DTO’ları, transaction referansları, testler ve persistence şeması gibi birçok alanı etkileyebileceği için bu aşamada refactor edilmemesine karar verildi.

---

## Gün Sonu Çıkarımı

Bu çalışmada önemli olan yalnızca kod yazmak değil, yanlış abstraction’ın fark edilip geri alınması oldu.

Sonuç:

```text
Domain içine persistence için magic ID değeri eklenmeyecek
ID üretimi application service’te tutulmayacak
Repository/persistence katmanı ID üretimini yönetecek
PostgreSQL kendi ID’sini üretecek
InMemory adapter kendi ID’sini üretebilecek
Customer ve Account ID’leri şimdilik ayrılmayacak
```
