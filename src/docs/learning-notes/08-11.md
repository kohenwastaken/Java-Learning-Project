# 08-11 — Persistence Katmanında ID Üretiminin Tamamlanması

## Günün Amacı

Customer ve Transaction ID üretimini `BankService` içindeki sayaçlardan çıkarıp repository/persistence katmanına taşımak.

Bu değişiklikle application service’in ID üretim mekanizmasını bilmemesi ve InMemory ile PostgreSQL implementasyonlarının kendi teknik ihtiyaçlarını kendi içinde yönetmesi hedeflendi.

---

## Customer ID Üretimi

`CustomerRepository` portuna yeni kayıt oluşturmayı ifade eden:

```java
Customer create(
        String name,
        String surname,
        String password
);
```

methodu eklendi.

Böylece `BankService` içindeki:

```java
private int userId = 1;
```

sayacı kaldırıldı ve müşteri oluşturma işlemi:

```java
Customer customer = customerRepository.create(
        name,
        surname,
        password
);
```

şeklinde değiştirildi.

InMemory implementasyonu kendi `nextCustomerId` sayacını kullanırken PostgreSQL adapterı ID üretimini veritabanına bırakacak şekilde hazırlandı.

`CustomerJpaEntity` primary key alanına:

```java
@GeneratedValue(strategy = GenerationType.IDENTITY)
```

eklendi.

---

## Transaction ID Üretimi

Aynı yaklaşım Transaction tarafında da uygulandı.

`TransactionRepository` portuna:

```java
Transaction create(
        Transaction.TransactionType type,
        BigDecimal amount,
        int sourceId,
        Integer targetId
);
```

methodu eklendi.

`InMemoryTransactionRepository`, kendi `nextTransactionId` sayacını kullanacak şekilde güncellendi.

`PostgreSqlTransactionRepositoryAdapter`, yeni transaction oluştururken ID alanını `null` bırakarak persistence katmanının ID üretmesini sağlayacak şekilde değiştirildi.

`TransactionJpaEntity` primary key alanına:

```java
@GeneratedValue(strategy = GenerationType.IDENTITY)
```

eklendi.

---

## BankService İçindeki Transaction Sayacının Kaldırılması

Eski:

```java
private int transactionId = 1;
```

sayacı tamamen kaldırıldı.

Deposit, withdrawal ve transfer işlemlerinde artık doğrudan:

```java
transactionRepository.create(...)
```

kullanılıyor.

Örneğin deposit:

```java
transactionRepository.create(
        Transaction.TransactionType.DEPOSIT,
        amount,
        account.getAccId(),
        null
);
```

Transfer:

```java
transactionRepository.create(
        Transaction.TransactionType.TRANSFER,
        amount,
        senderAccount.getAccId(),
        receiverAccount.getAccId()
);
```

şeklinde kaydediliyor.

---

## Katman Sorumluluklarının Son Hâli

```text
BankService
→ ID üretmez

Repository portları
→ create sözleşmesini tanımlar

InMemory adapter
→ kendi ID’sini üretir

PostgreSQL adapter
→ ID üretimini PostgreSQL’e bırakır

Domain modelleri
→ ID üretim teknolojisini bilmez
```

Bu yapı hexagonal architecture’ın application/domain katmanlarını infrastructure detaylarından ayırma amacına uygundur.

## Test Sonucu

Değişikliklerden sonra:

```bash
mvn clean test
```

çalıştırıldı ve:

```text
BUILD SUCCESS
```

sonucu alındı.

Bu, mevcut unit testlerin yapılan refactor ile uyumlu olduğunu doğrular. Ancak henüz PostgreSQL ile gerçek entegrasyonun test edildiği anlamına gelmez; gerçek veritabanı entegrasyonu ayrıca doğrulanacaktır.

---

## Gün Sonu Çıkarımı

Customer ve Transaction ID üretimi artık `BankService` içinde tutulmamaktadır.

Application service yalnızca iş akışını yönetirken, ID üretimi kullanılan repository implementasyonunun sorumluluğuna bırakılmıştır.

Bu sayede uygulama restartlarında Java içindeki sayaçların sıfırlanmasına bağlı ID çakışması riski ortadan kaldırılacak şekilde persistence tasarımı hazırlanmıştır.
