# 08-05 — ID Üretimi ve Persistence Lifecycle

## Günün Amacı

Bu çalışmada uygulamadaki ID üretim yaklaşımının PostgreSQL kalıcılığıyla neden uyumsuz olduğu incelendi.

Mevcut `BankService` içinde müşteri ve transaction ID’leri application katmanında sayaçlarla üretiliyordu:

```java
private int userId = 1;
private int transactionId = 1;
```

In-memory kullanımda çalışan bu yaklaşımın kalıcı veritabanına geçildiğinde sorun çıkarabileceği görüldü.

---

## Mevcut ID Üretimi

Müşteri oluştururken:

```java
Customer customer =
        new Customer(name, surname, password, this.userId);

Account account =
        new Account(this.userId, INITIAL_BALANCE);

this.userId++;
```

Transaction oluştururken:

```java
Transaction transaction = new Transaction(
        this.transactionId++,
        Transaction.TransactionType.DEPOSIT,
        amount,
        account.getAccId(),
        null
);
```

ID üretiminin sorumluluğu `BankService` içindeydi.

---

## PostgreSQL ile Neden Problem Oluşur?

Application içindeki sayaçlar yalnızca çalışan Java process’inin belleğinde tutulur.

Uygulama kapatılıp yeniden açıldığında:

```text
userId        → tekrar 1
transactionId → tekrar 1
```

olur.

PostgreSQL’de daha önce aynı primary key değerleri bulunuyorsa application yeniden aynı ID’leri üretmeye çalışabilir.

Sonuç olarak:

```text
Primary key conflict
Duplicate key
```

gibi hatalar oluşabilir.

---

## ID Üretiminin Persistence Katmanına Bırakılması

Kalıcı veritabanı kullanıldığında artan sayısal ID üretimini persistence katmanının yönetmesi daha uygundur.

Hedef yapı:

```text
BankService
→ Yeni kayıt isteği oluşturur
→ Repository / persistence katmanına gönderir
→ ID üretilir
→ ID verilmiş kayıt geri döner
```

Bu sayede application service son kullanılan ID gibi persistence ayrıntılarını takip etmek zorunda kalmaz.

---

## `@GeneratedValue`

JPA entity’lerinde primary key üretiminin persistence sistemine bırakılması için:

```java
@GeneratedValue
```

kullanılabilir.

Örnek:

```java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
@Column(name = "account_id")
private Integer accountId;
```

Yeni entity oluşturulurken ID henüz bulunmayabilir:

```text
accountId = null
```

Entity PostgreSQL’e kaydedildiğinde veritabanı ID üretir:

```text
null
↓
INSERT
↓
PostgreSQL
↓
17
```

Kaydedilmiş entity artık gerçek ID’ye sahiptir.

---

## `GenerationType.IDENTITY`

```java
@GeneratedValue(strategy = GenerationType.IDENTITY)
```

ile ID üretiminin veritabanının identity mekanizmasına bırakılması amaçlanır.

Bu sayede artan ID değerlerini Java application service içinde manuel olarak tutmaya gerek kalmaz.

---

## `save()` Sonucunun Önemi

Spring Data repository’nin:

```java
save(entity)
```

methodu kaydedilmiş entity’yi geri döndürür.

Bu nedenle:

```java
CustomerJpaEntity savedEntity =
        springDataRepository.save(entity);
```

şeklindeki kullanım önemlidir.

Veritabanının verdiği ID bu nesne üzerinden okunabilir ve daha sonra domain modeline dönüştürülebilir.

---

## InMemory Adapter Ne Yapacak?

PostgreSQL adapterında ID üretimi PostgreSQL’e bırakılabilir.

InMemory adapter’ın arkasında gerçek veritabanı olmadığı için test ve bellek içi kullanımda ID üretimini adapter kendisi yapabilir.

Hedef ayrım:

```text
PostgreSQL adapter → PostgreSQL ID üretir
InMemory adapter   → kendi ID’sini üretir
BankService        → nasıl üretildiğini bilmez
```

---

## Account ID Durumu

Mevcut projede `Customer` ve `Account` aynı ID değerini kullanmaktadır:

```text
Customer ID = 5
Account ID  = 5
```

Bu yapı bu aşamada korunmaktadır.

Müşteri ID’si üretildikten sonra aynı ID ile Account oluşturulması planlanmaktadır.

---

## Gün Sonu Çıkarımı

Ana problem ID’nin sayısal olması değil, ID üretiminin yanlış katmanda bulunmasıdır.

Eski yaklaşım:

```text
BankService
→ sayaç tutar
→ ID üretir
```

Hedef yaklaşım:

```text
BankService
→ kayıt oluşturma isteğini yapar
→ repository/persistence ID işini yönetir
```

Bu sayede ID üretimi application service’ten ayrılmış olur.
